## 2. Current code: the integration surfaces

All citations in this section are against the **current** working tree. PROJECT_DESIGN.md's own line citations predate Phases 0–3 and are systematically stale (see §4).

### 2.1 MCP server surface (deliverables 2, 4, 5, 6)

**Server construction and capabilities.** [src/index.ts](../../src/index.ts) uses the **low-level SDK `Server` class** with `setRequestHandler`, not `McpServer` ([index.ts:3](../../src/index.ts:3)). The server is constructed at [index.ts:61-72](../../src/index.ts:61) declaring capabilities `{ tools: {}, resources: {} }` — **no `prompts` capability and no `listChanged` flag on anything**. Transport is stdio ([index.ts:416-417](../../src/index.ts:416)). Startup runs `autoUpdateAll()` before connecting unless `CLEANROOM_MCP_SKIP_AUTO_UPDATE` is set ([index.ts:396-414](../../src/index.ts:396)).

**Resources are stubbed, prompts absent.** `ListResources` returns `{ resources: [] }` ([index.ts:383-387](../../src/index.ts:383)); `ReadResource` always throws `Resource not found` ([index.ts:390-393](../../src/index.ts:390)). No `ListResourceTemplates` handler, no subscriptions, zero prompt handlers, and no prompt schema imports ([index.ts:5-10](../../src/index.ts:5)). Deliverable 4 fills existing wiring; deliverable 5 has no wiring at all yet.

**SDK capability mechanics (verified against SDK source).** The pinned `@modelcontextprotocol/sdk` `^1.29.0` ([package.json:75](../../package.json)) resolves to exactly **1.29.0, which is the newest published version** (registry checked 2026-07-22). Everything Phase 4 needs is exported from `@modelcontextprotocol/sdk/types.js`: `ListPromptsRequestSchema` (types.d.ts:1818), `GetPromptRequestSchema` (:1896), `ListResourceTemplatesRequestSchema` (:1510), `SubscribeRequestSchema`/`UnsubscribeRequestSchema` (:1691/:1727), plus `PromptSchema`/`ResourceSchema`/`ResourceTemplateSchema` and text/blob resource-contents schemas. The low-level `Server` + `setRequestHandler` style **fully supports prompts and resource templates — no `McpServer` migration is required**. One hard constraint verified in SDK source: `setRequestHandler` immediately asserts the corresponding capability (`assertRequestHandlerCapability`, `dist/esm/server/index.js:209-258`) — registering `ListPrompts`/`GetPrompt` handlers **without adding `prompts: {}` to the capabilities object throws at server startup** ("Server does not support prompts"). `resources/list`, `resources/templates/list`, and `resources/read` all key off the already-declared `resources` capability, so resource handlers need no capability change. `Server.registerCapabilities()` exists as an alternative before `connect`. The SDK also ships an RFC 6570 `UriTemplate` class (`shared/uriTemplate.js`: `isTemplate`/`expand`/`match`) importable without `McpServer`, and a `completable()` helper whose use would require declaring the separate `completions` capability.

**Prompt-argument constraint.** `GetPromptRequest.params.arguments` is a flat `Record<string, string>` (types.d.ts:1896-1914) — all prompt argument values are plain strings; there is no typed/structured argument support. `GetPromptResult` is `{ description?, messages: [{role: 'user'|'assistant', content: text|image|audio|resource_link|embedded-resource}] }`; embedded resources (`type: 'resource'` wrapping text or blob contents with a URI) are the spec-blessed way for a prompt to pull server-managed documentation into the conversation.

**Tool registration pattern (the Phase 3 precedent Phase 4 tools would follow).** Registration is two-part: (1) the `ListTools` handler starts from `BASE_TOOLS` (4 always-on tools defined inline with JSON-Schema `inputSchema`s, [index.ts:75-208](../../src/index.ts:75)) and conditionally pushes optional groups gated on static `isAvailable()` checks — `MOD_EXAMPLES_TOOLS`, `MAPPINGS_TOOLS`, and the Phase 3 `CLEANROOM_API_TOOLS` ([index.ts:211-234](../../src/index.ts:211)); (2) the `CallTool` handler is one switch on tool name ([index.ts:237-380](../../src/index.ts:237)) whose optional-DB cases are *not* re-gated — the handler itself guards (e.g. [cleanroomApi.ts:160](../../src/tools/cleanroomApi.ts:160)). Args are unpacked with `as` casts importing the handler's exported param types ([index.ts:361-375](../../src/index.ts:361)). Unknown tool names throw a bare `Error`, which the SDK converts to a JSON-RPC `InternalError`.

**Tool module conventions** ([src/tools/cleanroomApi.ts](../../src/tools/cleanroomApi.ts) is the freshest template; [src/tools/mappings.ts](../../src/tools/mappings.ts) mirrors it): exported const array of `{name, description, inputSchema}` with `type: 'object' as const` literals; enum values shared between schema and runtime guard via a single const (`KIND_VALUES` at [cleanroomApi.ts:19-30](../../src/tools/cleanroomApi.ts:19), spread into the schema and into a `ReadonlySet` runtime check); limit clamping `Math.min(Math.max(limit || 15, 1), 50)` ([cleanroomApi.ts:197](../../src/tools/cleanroomApi.ts:197); search_docs clamps 1–20 at [searchDocs.ts:67](../../src/tools/searchDocs.ts:67)); typed exported `Params` interfaces; DB-backed handlers instantiate the service and close in `try/finally`. Markdown output: `Found N …` header, `###` per hit with a badge line (`formatBadges`, [cleanroomApi.ts:112-142](../../src/tools/cleanroomApi.ts:112)), fenced code blocks, `---` separators, trailing italic next-step hint, and zero-result outputs ending in a `**Suggestions:**` list. Error envelopes: uninstalled-DB → normal text (no `isError`) with `NOT_INSTALLED_MESSAGE`/`OUTDATED_SCHEMA_MESSAGE` pointing at `cleanroom-modding-mcp manage` ([cleanroomApi.ts:95-109](../../src/tools/cleanroomApi.ts:95)); invalid input → base tools use `isError: true`, Phase 3 tools return guidance text without it; unexpected exceptions → per-handler catch returning `isError: true`.

**Gating-model implication (no precedent exists for Phase 4's shapes).** Every optional tool group today gates on a *separate optional DB's* `isAvailable()` ([index.ts:216-231](../../src/index.ts:216)). `find_equivalent`'s data lives inside **docs.db — the required, postinstall-downloaded, always-auto-updated DB** ([dbs.ts:44-54](../../src/dbs.ts:44)) — but a user's installed docs.db may predate the compiled equivalence data until a startup auto-update succeeds. `get_project_template`, the resources, and the prompts have **no DB at all**. There is no precedent for "gate on a table existing inside docs.db" nor for always-on tools backed by package-shipped content; whichever is chosen is a new convention. Also: the `tools` capability declares no `listChanged` ([index.ts:68](../../src/index.ts:68)) and the server never emits notifications, so a tool list that changes mid-session is never announced.

**npm packaging constraint (affects deliverables 4, 5, 6).** The published tarball ships **only** `["dist", "scripts/postinstall.js"]` ([package.json:38-41](../../package.json)); the build is plain `tsc` with no asset-copy step (tsconfig `outDir ./dist`, `rootDir ./src`). Non-TS files — guide markdown, vendored template files, YAML — would not reach npm users unless compiled into a DB, embedded as TS/JSON modules under `src/`, or added to `files` with a copy step. The failure mode is silent: everything works in the dev checkout and breaks only on end-user installs. Related footgun: `pnpm run clean:all` executes `rimraf dist data` ([package.json:60](../../package.json)) — it would delete a committed `data/equivalence/` corpus from the working tree.

**Tests.** [src/index.test.ts](../../src/index.test.ts) (756 lines) imports handler functions directly and asserts result shapes, validation errors, and clamping — there are **no MCP-protocol-level tests**: nothing exercises the server object, `ListTools` gating, or `CallTool` dispatch, so a missing capability declaration or switch case has no safety net today. The Phase 3 service-test precedent ([cleanroom-api-service.test.ts](../../src/services/cleanroom-api-service.test.ts)) pushes a fixture corpus through the real pipeline into a temp SQLite DB, plus integration tests gated on the real DB's presence and schema version.

**README state.** The tools section ([README.md:64-77](../../README.md)) says "Four base tools are always available; mappings and mod-examples tool groups register automatically…" — already stale post-Phase-3 (omits the cleanroom-api group despite its table row at :76). No Resources or Prompts section exists. [README.md:22](../../README.md) links to `DESIGN.md`, which in the working tree has been renamed to `docs/PROJECT_DESIGN.md` (uncommitted; the two files are byte-identical — see §4).

### 2.2 Data pipeline and distribution (deliverable 1's compile path; deliverable 6's refresh path)

**docs.db build pipeline.** [scripts/index-docs.ts](../../scripts/index-docs.ts) is the entry point: opens a `DocumentStore` at repo-local `./data/docs.db` (:140-145 — the build writes to `./data`, distinct from the runtime platform data dir); discovers per-loader sources via the registry (`INDEXABLE_LOADERS` = loaders with non-empty `sources`, :47; per-loader switch :57-94 — fabric/neoforge/forge via sitemaps, cleanroom via `getCleanroomWikiPages()` with a VitePress `hashmap.json` fallback); crawls (:167-187); **merges pre-built repo-markdown pages into the same documents array after crawling** (:188-191) — this `prebuiltPages` path is the existing hook where non-crawled corpora enter the pipeline; chunks (max 1000 chars, overlap 100, :195-199); embeds (`Xenova/all-MiniLM-L6-v2`, :243); stores. Flags: `--force`, `--incremental`, `--sitemap`, `--embeddings`, `--loaders a,b`. **There is no "compile extra data" stage today** — everything flows through documents/chunks.

**docs.db schema** ([src/indexer/store.ts:64-188](../../src/indexer/store.ts:64), `SCHEMA_VERSION = 1` hardcoded at [store.ts:9](../../src/indexer/store.ts:9)): `metadata(key, value)`; `documents(id, url UNIQUE NOT NULL, title, content, raw_html, category, loader, minecraft_version, hash, …)`; `sections`; `code_blocks`; `chunks`; `embeddings(chunk_id, embedding BLOB, dimension, model, …)`; FTS5 `documents_fts` + `chunks_fts` with sync triggers; 7 indexes. `loader` and `category` are free TEXT with no CHECK constraints ([store.ts:79-80](../../src/indexer/store.ts:79)). `storeDocument` is `INSERT OR REPLACE` keyed on `url` ([store.ts:214-229](../../src/indexer/store.ts:214)). Metadata is seeded with `INSERT OR IGNORE` ([store.ts:193-198](../../src/indexer/store.ts:193)) — an existing DB opened by newer code never gets its `schema_version` rewritten; correctness currently depends on the weekly job's `rm -f` full-rebuild convention.

**Repo-markdown ingestion precedent (closest analog for vendored templates and guides).** [src/indexer/cleanroom-wiki.ts](../../src/indexer/cleanroom-wiki.ts): lists `CleanroomMC/Website` blobs via the GitHub `git/trees` API, filtered to `.md` under `includeTrees` (default `['docs/wiki/']` — the option at [cleanroom-wiki.ts:89-92](../../src/indexer/cleanroom-wiki.ts:89) is explicitly documented as the slot for future corpora), fetches from `raw.githubusercontent.com` with retries, maps repo paths to canonical published routes ([cleanroom-wiki.ts:61-67](../../src/indexer/cleanroom-wiki.ts:61)), honors `GITHUB_TOKEN`. [src/indexer/markdown.ts](../../src/indexer/markdown.ts) converts one markdown file to a `DocumentPage`: a **deliberately dependency-free minimal YAML frontmatter parser** (title + tags only; the comment at [markdown.ts:41-42](../../src/indexer/markdown.ts:41) notes it avoids a YAML dependency), sections from ATX headings, 16-char sha256 change-detection hash. `MarkdownPageInput` requires a canonical `url`, the raw markdown, and a `loader` typed as the `Loader` union ([markdown.ts:15-23](../../src/indexer/markdown.ts:15)).

**No YAML parser exists anywhere in the tree.** Dependencies ([package.json:74-83](../../package.json)) contain no YAML lib; `js-yaml` and `yaml` appear only transitively in `pnpm-lock.yaml` and are not hoisted (verified: `require` fails for both). Parsing `data/equivalence/*.yaml` requires the repo's **first YAML dependency** (build-only devDependency if compiled solely by scripts; runtime dependency if any `dist/` code reads YAML) or extending the minimal parser. House conventions: pnpm with `--frozen-lockfile` in CI, caret ranges (one exact pin: `tree-sitter-java`), native/build-script packages allowlisted in `pnpm.onlyBuiltDependencies`.

**DB registry and schema-gate machinery.** [src/dbs.ts](../../src/dbs.ts) is the single source of truth (`PACKAGE_NAME`, `REPO_SLUG`, `DbId = 'docs'|'mappings'|'examples'|'cleanroom-api'`, per-DB `fileName`/`manifestName`/`required`/`schemaVersion`; docs is the only `required: true`, schemaVersion 1, [dbs.ts:44-54](../../src/dbs.ts:44)). Optional-DB services implement `isAvailable()` as `readDbSchemaVersion(path) === spec.schemaVersion` with an mtime cache; **the docs services have no such gate** — `DocumentStore`'s constructor creates the schema if the file is missing ([store.ts:56-59](../../src/indexer/store.ts:56)), so opening a nonexistent docs.db silently creates an empty one, and an old-schema docs.db paired with new query code would fail at query time rather than degrade gracefully. Schema-change precedent (mappings v1→v2, cleanroom-api): **no migration code exists anywhere** — every schema change is a full rebuild plus client force-redownload via `DbVersioning.isUpdateAvailable`'s "schema forcing function" ([db-versioning.ts:187-199](../../src/db-versioning.ts:187), generic over any DB with a metadata table, docs.db included). The mappings/cleanroom-api DDL files carry a "bump together with `DBS.….schemaVersion`" comment; [store.ts:9](../../src/indexer/store.ts:9) has **no such link** to [dbs.ts:51](../../src/dbs.ts:51).

**How an equivalence change would reach users under current machinery** (operational facts, assuming compile-into-docs.db): docs.db is fully rebuilt **only by the weekly job** (Sunday 02:00 UTC from `dev`, [update-docs-weekly.yml:5-6,58-67](../../.github/workflows/update-docs-weekly.yml)) and uploaded with `--clobber` onto the **latest existing release** with a patch-bumped manifest; the **release workflow does not rebuild docs.db** — it carries the previous release's docs.db forward verbatim (`carry_forward()`, [release.yml:188-226](../../.github/workflows/release.yml)), except on a first-ever release. Net cadence: YAML merged to `dev` becomes user-visible after the next successful Sunday run *and* the user's next server start; publishing a release ships no new equivalence data. The weekly docs step has no no-op skip (unlike cleanroom-api's `CLEANROOM_API_CHANGED` gating, [update-docs-weekly.yml:137-188](../../.github/workflows/update-docs-weekly.yml)) — it unconditionally rebuilds and re-uploads ~26 MB with a version bump, and its success depends on the full external crawl finishing inside the 180-minute budget. Manifest-continuity hazard: every manifest step downloads the previous manifest with `|| true`; if that fetch fails, `--bump` restarts at 0.1.x and higher-versioned clients silently skip all future updates (warned in-file at [update-docs-weekly.yml:176-178](../../.github/workflows/update-docs-weekly.yml)). `workflow_dispatch` is the existing manual escape hatch. The weekly job **never commits to git** — a template-refresh step that vendors snapshots into the repo would be its first git-writing step, or must deliver through a DB/release asset instead.

**Pinned-upstream-version precedent (relevant to "templates pinned to a Cleanroom version").** The cleanroom-api indexer records `cleanroom_version`, sources-jar URL, jar sha256, and parser info into DB metadata at ingest ([scripts/index-java-api.ts:299-304](../../scripts/index-java-api.ts:299)) and uses it for the weekly no-op skip ([index-java-api.ts:198-216](../../scripts/index-java-api.ts:198)).

### 2.3 Consumer surfaces (deliverables 2, 3, and discovery)

**Loader registry.** [src/loaders.ts:17-19](../../src/loaders.ts:17): `Loader = 'cleanroom'|'forge'|'fabric'|'neoforge'|'shared'`; `Scope = 'target'|'reference'|'all'`; roles: cleanroom/forge `target` (defaultVersion `1.12.2` via `TARGET_VERSION`, :41), fabric/neoforge `reference` (defaultVersion `null` = derive latest from indexed data), shared `neutral`. `TARGET_FAMILY = [cleanroom, forge, shared]`, `REFERENCE_FAMILY = [fabric, neoforge, shared]` (:102-108). `LOADER_IDS` feeds every tool-schema loader enum ([index.ts:97,153,191](../../src/index.ts:97)).

**The `modern-minecraft` gap.** `find_equivalent`'s planned `from` enum includes `'modern-minecraft'`, which is **not a `Loader` value and has no representation in the registry** — it is a version-era concept. `isLoader('modern-minecraft')` is false; unknown loader values are silently dropped by search/get_example ([searchDocs.ts:85-88](../../src/tools/searchDocs.ts:85), [getExample.ts:66](../../src/tools/getExample.ts:66)) and silently coerced to the `cleanroom` default by explain_concept ([explainConcept.ts:32-34](../../src/tools/explainConcept.ts:32)). `'shared'` cannot stand in for it: shared belongs to **both** families (:102-108), so labeling backport-source rows `shared` would leak them into target scope. Typing it as a `Loader` would ripple into `LOADER_IDS`-driven schemas, `scopeToLoaders`, both families, and `list_targets`' matrix; keeping it out means a separate from-vocabulary. This is a design decision with no current-code answer (Open Question 5).

**Concept service.** `KNOWN_CONCEPTS` ([concept-service.ts:63-237](../../src/services/concept-service.ts:63)) holds **30 entries** (21 cross-loader + 9 added for 1.12.2 under the §4.1 comment at :151: capabilities, srg names, coremods, mcmod.info, creativetabs, oredictionary, mixinbooter, gameregistry, access transformers). The old Fabric semantic-query bias is gone (`Explain ${concept} ${loaderPhrase(loader)}`, :527-529). Java-token hints are role-split into `TARGET_CONCEPT_PATTERNS` (1.12.2 idiom, :244-289) and `REFERENCE_CONCEPT_PATTERNS` (:291-311). Output assembly: `ConceptExplanation` struct (:18-42) → `formatForAI` renders fixed markdown sections (:916-974) → the handler appends a "Limited information" block when `sourcesUsed < 2` ([explainConcept.ts:74-81](../../src/tools/explainConcept.ts:74)). A difference banner has two natural attach points matching existing precedent: prefix concatenation in the handler (the searchDocs banner pattern) or a new field on `ConceptExplanation` rendered inside `formatForAI` — the interface has no field for equivalence data today. Caution: alias matching is bidirectional-substring (`expandConcept`, :442-466) with an in-code warning about over-matching — keying banner attachment on it risks false positives. Input caps: concept ≤100 chars ([explainConcept.ts:52-62](../../src/tools/explainConcept.ts:52)).

**Scope semantics and the existing reference banner.** `search_docs` defaults `scope` to `target` with silent coercion of invalid values ([searchDocs.ts:23,47-49](../../src/tools/searchDocs.ts:23)); explicit `loader` overrides scope. The Phase-1 **"Porting reference" banner exists**: scope `reference` with no explicit loader prepends a `> ⚠️ **Porting reference**…` blockquote ([searchDocs.ts:123-129,138](../../src/tools/searchDocs.ts:123)). Two nuances: the banner is **suppressed whenever an explicit loader filter is set** (searching `loader: 'fabric'` directly yields no banner), and its text does not yet mention `find_equivalent` (the design's §4.1 wording anticipated Phase 4). `get_example` has **no** banner at all despite §7.1's "reference-scope output is visually marked."

**Categories.** [src/categories.ts](../../src/categories.ts): `DOC_CATEGORIES` = 12 values (:10-23), `EXAMPLE_CATEGORIES` = 21 values (:33-55, currently consumed only by its test — no runtime consumer), `CONCEPT_CATEGORIES` = 16 (:58-64), `categorizeDocPath` with `general` fallback. No category slot exists for equivalence content.

**`list_targets` (the orientation tool).** [src/tools/listTargets.ts:15-95](../../src/tools/listTargets.ts:15) reports the loader/role/version matrix, a Scopes explainer **hardcoding** "accepted by search_docs / get_example" (:28-32), indexed versions, and per-DB install status with ⚠️/✅/⬜ glyphs. It reports **nothing** about resources, prompts, templates, or equivalence — there is no discovery surface for Phase 4 capabilities, and the tool description tells agents to "call this first in a new session."

**Search mechanics that constrain compiled-in equivalence documents** (facts, given the design compiles entries into docs.db):

- `documents.url` is `UNIQUE NOT NULL` with `INSERT OR REPLACE` keyed on url — every compiled entry needs a distinct stable URL, and collisions silently overwrite curated data.
- `deduplicateByUrlPath` collapses results whose URLs differ only by a version-like path segment (regex strips `/\d+\.\d+(\.\d+)?/`, [search-service.ts:354-413](../../src/services/search-service.ts:354)) — synthetic URLs embedding version segments would merge distinct entries.
- Version-filtered searches **exclude** documents with NULL `minecraft_version` ([store.ts:1121-1125](../../src/indexer/store.ts:1121)); target-scope "latest" resolves to 1.12.2.
- `documents.loader` is a single value per document, and scope filtering is a plain `loader IN (...)` ([store.ts:27-51](../../src/indexer/store.ts:27)) — an equivalence entry inherently spans a from-loader and a to-loader; a fabric-labeled entry is invisible in default target scope, a shared-labeled one surfaces unmarked in target results.
- URLs print verbatim in agent-facing output (search results, concept resources, code-example sources).
- Vocabulary: `COMMON_TERMS` already down-weights `cleanroom` and `forge` ([search-utils.ts:51-65](../../src/services/search-utils.ts:51)); `MINECRAFT_SYNONYMS` has the blockentity↔tile-entity bridge but nothing for capabilities/oredict/creativetabs/srg/coremod/mixinbooter/access-transformers (:70-121); `CODE_PATTERNS` is still entirely modern/Fabric idiom with zero 1.12.2 tokens (:126-140) — 1.12.2 token vocabulary lives only in concept-service's `TARGET_CONCEPT_PATTERNS`, which the docs/example search path does not use.

### 3.1 CleanroomModTemplate (source for deliverables 4 and 6)

Verified via the GitHub API and raw file reads on 2026-07-22 (`github.com/CleanroomMC/CleanroomModTemplate`).

**The design doc's toolchain description is wrong for the template.** [PROJECT_DESIGN.md:201](../PROJECT_DESIGN.md) says `get_project_template` serves "build.gradle (Outlands ForgeGradle 6.0.57 coordinates…)". The FG-6.0.57 fact is true of the Cleanroom **loader's own build** ([PROJECT_DESIGN.md:87](../PROJECT_DESIGN.md)), but the official mod template **does not use ForgeGradle at all** — repo description: *"Mod development template for Cleanroom, uses Unimined."* build.gradle applies `xyz.wagyourtail.unimined` version **`1.4.26-kappa`**, a personal Unimined fork by kappa-maintainer resolved from `maven.arcseekers.com/releases` (plugin-marker POM verified live; the README warns the fork "may have issues"). Other plugins: `com.gradleup.shadow` 9.5.1, `net.kyori.blossom` 2.2.0 (token replacement), idea-ext, foojay-resolver. Gradle wrapper 9.6.1. ### 3.3 MCP resources & prompts: spec and client reality (deliverables 4, 5)

**Spec.** Current revision **2025-11-25** (modelcontextprotocol.io/specification/versioning); nothing in it structurally changes resources/prompts vs 2025-06-18 (adds icons metadata, experimental tasks, elicitation tweaks). Resources are an **application-driven** primitive (the host decides surfacing); a custom `cleanroom://` scheme is explicitly legitimate — the spec says implementations are free to use custom URI schemes (RFC 3986-conformant) and servers *SHOULD* prefer a custom scheme over `https://` for content the client can't fetch from the web. Resource templates use RFC 6570; not-found SHOULD be JSON-RPC `-32002`. Prompts are a **user-controlled** primitive — the spec's own illustrative surfacing is slash commands; `prompts/get` takes flat string arguments and returns messages that may embed resources; invalid name/missing args are `-32602`.

**Client support reality (per-vendor docs, verified 2026-07-22).** The official client feature matrix formerly at `modelcontextprotocol.io/clients` **has been removed** (redirects to the homepage) — the design doc cannot cite it. Per-client:

- **Claude Code** (primary consumer, per code.claude.com/docs/en/mcp): resources surface as `@server:protocol://resource/path` mentions with fuzzy autocomplete, fetched as attachments; additionally Claude Code "automatically provides tools to list and read MCP resources" — i.e. resources **are model-fetchable there**, which weakens (but does not eliminate) the tool-twin rationale for that client. Prompts become slash commands `/mcp__server__prompt` with space-separated, quotable arguments "parsed based on the prompt's defined parameters." Supports `list_changed` for tools/prompts/resources with auto-refresh. Caps: MCP tool results ~25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`); tool descriptions and server instructions truncated at 2 KB in tool-search mode.
- **Claude.ai / Claude Desktop** (claude.com/docs/connectors/building): tools, prompts, and resources (text + blob) supported; **resource subscriptions and sampling explicitly not supported**; tool-result cap ~150,000 characters / 300 s.
- **VS Code Copilot**: tools, resources (user-attached via "Add Context → MCP Resources"), prompts as `/server.prompt` slash commands.
- **Cursor**: docs claim tools, prompts, resources, roots, elicitation — but document UI surfacing only for tools. **Cline**: documents tools only. **Zed**: current docs URL 404s; dated community evidence suggests tools + prompts-as-slash-commands.
- **Resource templates**: **no client doc surveyed provides any evidence of `resources/templates/list` support** — if the design relies on a `cleanroom://template/{component}` URI template rather than enumerating concrete URIs in `resources/list`, no surveyed client is known to surface it. Empirically testable against a dev build (Open Question 17).

Net: the design premise "client support for resources is uneven" ([PROJECT_DESIGN.md:204](../PROJECT_DESIGN.md)) is directionally right but should be restated: all primary Claude surfaces now claim resources support; the real unevenness is **how** they surface (user-attached vs model-fetchable) and resource-template support. The every-resource-has-a-tool-twin rule remains justified on those grounds. Prior art is consistent: existing scaffold MCP servers predominantly ship template content as tools.

### 3.4 Equivalence corpus source material (deliverable 1)

#### 3.4.1 The era problem (the single biggest authoring fact)

Mojang announced on 2025-10-29 that Minecraft Java ships unobfuscated; versioning switched to year-based (1.21.11 is the last obfuscated version; 26.1 shipped ~2026-03, then 26.2). **Fabric froze Yarn and Intermediary after 1.21.11** (fabricmc.net/2025/12/05/12111.html, fabricmc.net/2026/03/14/261.html, docs.fabricmc.net/develop/porting/mappings/). Consequences verified directly:

- **docs.fabricmc.net retroactively re-renders even old-version pages into Mojang mappings.** Confirmed twice: the 1.21.1 first-item page now shows `BuiltInRegistries.ITEM` / `ResourceLocation` / `Item.Properties` — names real 1.21.1 Fabric mods (written in Yarn: `Registries.ITEM`, `Identifier.of`, `Item.Settings`) do not contain; the 1.20.4 page mixes Mojang names with residual `FabricItemSettings`. **Do not cite docs.fabricmc.net for Yarn-era spellings, even on versioned pages.**
- Fabric API classes were themselves renamed in the 26.x era (verified: `ItemGroupEvents.modifyEntriesEvent` @1.21.1 vs `CreativeModeTabEvents.modifyOutputEvent` @26.2; `ActionResult` vs `InteractionResult`); "access wideners" became "class tweakers" (`.classtweaker`).
- NeoForge ≤1.20.1 is API-identical to Forge 1.20.1, not to anything on docs.neoforged.net (whose version selector starts at 1.20.3/1.20.4).

Realistic porting inputs therefore span **at least four source eras** the corpus's `from.versions` model must express: (a) Yarn-named Fabric ≤1.21.11 (most portable Fabric mods), (b) Mojang-named Fabric 26.x, (c) pre-1.20.5-networking Fabric (1.16–1.20.4: `Identifier` channels + `PacketByteBuf`), and (d) **"legacy modern Forge" 1.16–1.20.1** (`DeferredRegister`/`RegistryObject`, `SimpleChannel`, `LazyOptional` capabilities) — a huge share of real ports that neither current-Fabric nor current-NeoForge docs describe.

#### 3.4.3 Per-topic verified API names

Every name below was verified against a live page/javadoc this recon (source given); names that could **not** be verified are flagged.

**Registration.**
- Fabric 26.2: `Registry.register(BuiltInRegistries.ITEM, itemKey, item)` with `ResourceKey<Item>`; `Item.Properties.setId(itemKey)` now mandatory (~1.21.2+); creative tab via `CreativeModeTabEvents.modifyOutputEvent` (docs.fabricmc.net/develop/items/first-item). Fabric 1.21.1 (Yarn era): plain `ResourceLocation`/`Identifier`, `ItemGroupEvents.modifyEntriesEvent` (versioned page + fabric-api 0.116.14 javadoc).
- NeoForge 26.1: `DeferredRegister.create`, `DeferredHolder<R, T>`, specialized `DeferredRegister.Blocks/.Items/.DataComponents`, mod-bus attach, `RegisterEvent` alternative (docs.neoforged.net/docs/concepts/registries/).
- Forge 1.16–1.20.1: `DeferredRegister` + `RegistryObject` (docs.minecraftforge.net/en/1.16.x/concepts/registries/, 14+ mentions each).
- 1.12.2 target: `RegistryEvent.Register<T>` (fires alphabetically by type; Block always before Item; ItemBlock registered separately), `event.getRegistry().registerAll`, `IForgeRegistryEntry.Impl#setRegistryName`, `@ObjectHolder` (injection refreshed between rounds), `GameRegistry` as superseded utility, `RegistryEvent.NewRegistry` + `RegistryBuilder` (docs.minecraftforge.net/en/1.12.x/concepts/registries/). Naming trap: NeoForge's `RegisterEvent` vs 1.12.2's `RegistryEvent.Register` are near-homonyms with different semantics.

**Events / lifecycle.**
- Fabric: callback interfaces on `Event<T>` objects (`AttackBlockCallback.EVENT.register`, `UseItemCallback`, `ServerTickEvents`), listeners return `InteractionResult` (Yarn: `ActionResult`); lifecycle from `fabric.mod.json` entrypoints `main`/`client`/`server` (`ModInitializer` etc.) (docs.fabricmc.net/develop/events; wiki fabric_mod_json spec).
- NeoForge: two buses (game bus `NeoForge.EVENT_BUS`, mod bus via constructor), `@SubscribeEvent`, `@EventBusSubscriber`; lifecycle mod-bus events `FMLConstructModEvent`, `FMLCommonSetupEvent`, `FMLClientSetupEvent`, `FMLDedicatedServerSetupEvent`, `FMLLoadCompleteEvent` (docs.neoforged.net/docs/concepts/events/).
- 1.12.2 target: **single** main bus `MinecraftForge.EVENT_BUS` (plus `TERRAIN_GEN_BUS`/`ORE_GEN_BUS` — field names verified via ForgeJavaDocs-NG `MinecraftForge.html`), `@SubscribeEvent`, `@Mod.EventBusSubscriber`, `@Cancelable`, `@HasResult`/`Event.Result`; lifecycle is **not bus events** but `@Mod.EventHandler` methods receiving `FMLPreInitializationEvent`/`FMLInitializationEvent`/`FMLPostInitializationEvent`/`FMLServerStartingEvent` (docs.minecraftforge.net/en/1.12.x/events/intro/, /conventions/loadstages/). Pattern-change: Neo's mod-bus/game-bus split collapses to one bus + `@Mod.EventHandler` lifecycle.

**Networking.**
- Fabric ≥1.20.5 (rewrite noted on the docs page): payload records implement `CustomPacketPayload` (Yarn: `CustomPayload`) + `StreamCodec` (Yarn: `PacketCodec`); `PayloadTypeRegistry.clientboundPlay()/serverboundPlay()` (Yarn: `playS2C()/playC2S()` — verified in fabric-api 0.116.14+1.21.1 javadoc); `ServerPlayNetworking`/`ClientPlayNetworking` send/registerGlobalReceiver.
- Fabric pre-1.20.5 (the era most portable mods use): `ServerPlayNetworking.registerGlobalReceiver(Identifier, PlayChannelHandler)`, `ClientPlayNetworking.send(Identifier, PacketByteBuf)` (package `…api.client.networking.v1`), `PacketByteBufs.create()` — all verified in fabric-api 0.92.11+1.20.1 javadoc; secondary source wiki `tutorial:networking`.
- NeoForge 26.1: `CustomPacketPayload` + `CustomPacketPayload.Type` + `StreamCodec`, `RegisterPayloadHandlersEvent` → `PayloadRegistrar.playToClient/playToServer/playBidirectional`, `PacketDistributor.sendToPlayer`, `IPayloadContext.enqueueWork()` (docs.neoforged.net/docs/networking/payload/).
- Forge 1.16–1.20.1: `SimpleChannel` (docs.minecraftforge.net/en/1.16.x/networking/simpleimpl/).
- 1.12.2 target: `NetworkRegistry.INSTANCE.newSimpleChannel` → `SimpleNetworkWrapper`; packets implement `IMessage`, handlers `IMessageHandler#onMessage(msg, MessageContext)`; `registerMessage(Handler, Message, discriminatorId, Side)`; send via `sendToServer/sendTo/sendToAll/sendToDimension/sendToAllAround(TargetPoint)/sendToAllTracking`; **packets handled on the network thread since 1.8 — main-thread work must go through `IThreadListener.addScheduledTask`** (documented verbatim at docs.minecraftforge.net/en/1.12.x/networking/simpleimpl/). `enqueueWork`/Fabric `execute()` map to `addScheduledTask`; the discriminator byte + `Side` registration is the other pattern-change.

**Mixins, access wideners, access transformers.**
- Fabric: mixin configs declared in `fabric.mod.json` `"mixins"` array (wiki spec page, live 2026-03-30); access wideners → **class tweakers** (`accessible`/`extendable`/`mutable`, `.classtweaker`, vanilla classes only) (docs.fabricmc.net/develop/class-tweakers/access-widening); canonical mixin refs remain the SpongePowered and MixinExtras GitHub wikis.
- NeoForge: `META-INF/accesstransformer.cfg`, build.gradle declaration, `<modifier> <fq class> <member><descriptor>` (docs.neoforged.net/docs/advanced/accesstransformers/).

## 5. Constraints and risks (consolidated)

**Hard technical constraints:**

- **C1 — prompts capability crash.** Registering prompt handlers without adding `prompts: {}` at [index.ts:66-71](../../src/index.ts:66) throws at startup (SDK capability assertion, §2.1). No existing test would catch it — nothing exercises the server object.
- **C2 — npm tarball blind spot.** Only `dist/` + `postinstall.js` ship; plain-`tsc` build copies no assets. Any Phase 4 file read from disk at runtime works in the dev checkout and silently breaks for npm users (§2.1).
- **C3 — prompt arguments are flat strings** (§2.1); structured scaffold parameters need an encoding convention or few simple args.
- **C4 — client result caps** bound template/guide payloads: ~25K tokens (Claude Code) / ~150K chars (Claude.ai/Desktop); per-component granularity avoids truncation. Resource templates have no verified client support; subscriptions are explicitly unsupported on Claude surfaces (§3.3).
- **C5 — docs.db mechanics for compiled-in entries:** unique-URL overwrites, version-segment dedup collisions, NULL-version exclusion from filtered searches, single-loader scope routing, and the docs services' lack of any schema gate (§2.2, §2.3). A docs `schema_version` bump exercises the force-redownload path — which works generically — but old-schema DBs paired with new code fail at query time, and offline users stay broken indefinitely.

**Operational risks:**

- **R1 — freshness coupling.** Equivalence/guide updates ride the weekly docs rebuild: gated on a successful 180-minute external crawl, uploaded to the latest release, invisible to release publishing, fragile to the manifest-continuity hazard (§2.2).
- **R2 — template drift.** The template changed build systems repeatedly within months; CleanroomGradle looms as a successor; the kappa Unimined fork is a personal fork on a third-party maven; branches (mixin/kotlin/scala) are manually merged and can lag main. A refresh job tracking only `main` misses the mixin wiring entirely; there are no tags to pin, only commit SHAs (§3.1).
- **R3 — corpus staleness.** Cleanroom released 0.6.3-alpha the day of this recon; MixinBooter's wiki was rewritten for 11.x two days prior; Fabric/NeoForge current names churned within months (26.x renames, NeoForge 21.9 transfer rework). Entries need version-pinned `from.versions`/`to` data and a recorded validated-against version (§3.4).
- **R4 — link rot / citation drift.** docs.fabricmc.net silently re-renders old pages into wrong-era names; unversioned NeoForge URLs move; ForgeJavaDocs-NG is single-maintainer; mcforge.readthedocs.io is a redirect, not a mirror. Entries that rely on a linked page continuing to show a name will silently desynchronize — quoting load-bearing names inline is the robust pattern; link-checking is not currently in any CI job (§3.4.2).
- **R5 — licensing gates.** CleanroomMC/Website (wiki) has no license — both the existing docs.db wiki ingestion and any derived guide text depend on the not-yet-evidenced CleanroomMC blessing. Prior-art license split (LGPL vs Apache/MIT/CC-BY) constrains snippet derivation (§3.2, §3.4.4).
- **R6 — `clean:all` deletes `data/`** including a committed equivalence corpus (recoverable via git, but a footgun contradicting the .gitignore's own comment) (§2.1).
- **R7 — alias over-matching.** Keying banner attachment on `expandConcept`'s bidirectional-substring aliases risks attaching wrong-topic banners (§2.3).
- **R8 — no protocol-level test safety net** for any of Phase 4's new wiring (capability declarations, ListTools gating, resource/prompt handlers) (§2.1).
