### 2.3 Distribution machinery (examples as a generic registry entry)

- **Registry** ([src/dbs.ts](../../src/dbs.ts)): `PACKAGE_NAME = 'cleanroom-modding-mcp'` (:16), `REPO_SLUG = 'ndellagrotte/cleanroom-modding-mcp'` (:17), `DbId` union (:29). The examples spec (:65-74): `fileName: 'examples.db'`, `manifestName: 'examples-manifest.json'`, `required: false`, `schemaVersion: 1`, description *"Curated code examples from canonical open-source 1.12.2 mods"*, icon 🧩. Header comment (:8-10): all DB assets ride the main `v{version}` release — no per-DB tags. Release selection is asset-name-driven (`selectRelease`, :128-148).
- **`manage`** ([src/cli/manage.ts](../../src/cli/manage.ts)): examples is **not special-cased anywhere** — generic registry-driven menu (:907), generic download install (:1043-1061), no remove flow, no examples-specific messaging. The only per-DB branch is the **mappings local-build path** (:968 → `promptMappingsInstallMethod` :865-899 → `runLocalMappingsBuild` :807-845, manifest pinned `version: '0.0.0-local'` + `source: 'local-build'` so auto-update skips it; headless `manage --build-mappings` via [index.ts:47-56](../../src/index.ts:47)). **Examples has no analog** — a design choice the design doc must make explicitly (Open Question 19). Practical state today: the fork repo has **zero releases** (verified live), so every DB renders "Not installed … (offline)" (:722, :735) and examples install reports "Remote version unavailable" (:996-1002) — despite [README.md:53](../../README.md) promising install "via `manage`".
- **Startup auto-update** ([db-versioning.ts:414-429](../../src/db-versioning.ts:414)) covers examples generically **once installed** (optionals skipped when not installed). Local-build marker `LOCAL_BUILD_SOURCE` (:28, :160-166). The **schema forcing function** (:190-199) reads `metadata.schema_version` and force-replaces on mismatch — **but** `dbSchema !== null && …` (:192) means a legacy DB *without* a `metadata` table (§2.2) is treated as "don't force": the ancient 3-example DB dropped at the examples path would light up all five tools (existsSync gate, §2.2) and then fail at query time, unreplaced.
- **Manifest generation** ([scripts/generate-manifest.ts](../../scripts/generate-manifest.ts)): fully registry-driven (`--db examples` accepted, validated :68-70); `--release-tag` required (:71-73); download URL built as `{REPO_URL}/releases/download/{tag}/{fileName}` ([db-versioning.ts:358-359](../../src/db-versioning.ts:358)); `--bump` seeds from the previous manifest found **alongside the DB** at `./data/<manifestName>` (:81-98) — because `data/` is untracked, CI must download the previous release's manifest first or numbering restarts at `0.1.0` (the manifest-continuity hazard, also flagged for docs in Phase 4 R1).
- **postinstall** ([scripts/postinstall.js:6-12,25-35](../../scripts/postinstall.js)): docs.db only; examples is opt-in, never referenced.
- **Version-continuity landmine:** the ancient manifests were `0.1.1`/`0.2.0`. A new pipeline starting at `0.1.0` would produce manifests *lower* than any surviving old install's local manifest, so version comparison alone would never replace them (and the schema gate is null-toothless against them, above). Either the registry `schemaVersion` must bump (1→2) or the new manifest line must start above `0.2.0` (Open Question 9).

### 2.4 CI ([release.yml](../../.github/workflows/release.yml), [update-docs-weekly.yml](../../.github/workflows/update-docs-weekly.yml))

**CI does not build examples.db; it only carries it forward — and the carry-forward can never fire.** Release workflow: mappings always rebuilt (:88-113); cleanroom-api rebuilt with maven canary + verbatim carry-forward fallback (:115-168); docs and examples via `carry_forward()` (:188-223, invoked :225-226). `carry_forward` finds the newest other release carrying the asset; **if none: soft-skip with a warning and `return 0`** (:199-201) — not a failure. Asymmetry: docs has a fresh-build fallback (:232-247) and a fail-closed guard (`test -f release-artifacts/docs.db`, :250); **examples has neither**. The upload list already includes `examples.db` + `examples-manifest.json` (:255-268, `fail_on_unmatched_files: false` :259; body rows :284-285). The in-file comment states the intent (:184-187): *"fresh docs come from the weekly job, fresh examples from maintainer-run indexing."* Since no release anywhere has ever carried an examples asset (§2.2), every release silently ships without it. **"CI finally uploads the examples asset" therefore means adding an indexing step, not upload plumbing** — the plumbing has existed since `38f5715`.

**The weekly job never touches examples** — no occurrence of "example" in its 242 lines (sections: DOCUMENTATION :54-87, MAPPINGS :89-131, CLEANROOM API :133-188, UPLOAD :190-219). The **cleanroom-api change-gating pattern is the in-repo precedent** for a Phase 5 examples step: canary probe with graceful skip (`CLEANROOM_API_CHANGED=false` on outage, :144-150) → seed the working DB from the current release so the indexer's own up-to-date check can no-op (:152-157) → sha256 before/after comparison (:161-167) → manifest generation and upload **gated on the flag** (:169-188, :214-219) → summary handles all flag states (:233-239). What the examples analog uses as its change-detection key (roster SHAs? content hashes?) is an open design question (Open Question 18) — the cleanroom-api key is an upstream maven version, which examples lack.

- **Category drift (the §4.1 edits half-landed):** [EXAMPLE_CATEGORIES](../../src/categories.ts:28) (21 values, :33-55) carries the landed 1.12.2 edit with an explanatory comment (:28-32: `data-generation` removed, `capabilities` + `coremods-mixins` added) — but its **only consumer is its own test** ([categories.test.ts:9,33-46](../../src/categories.test.ts:9)); the runtime enum users actually see is the hardcoded 20-value inline schema in `search_mod_examples` ([modExamples.ts:33-54](../../src/tools/modExamples.ts:33)), which still lists `data-generation` and lacks both additions. ### 3.2 Licensing analysis for a verbatim-snippet database

The examples DB's entire purpose is storing and redistributing **verbatim code excerpts** — a different posture from Phase 4's equivalence corpus, where the established rule was "no LGPL-derived snippets in `code_before`/`code_after`" ([phase4/RESEARCH.md:219](../phase4/RESEARCH.md)). That rule cannot apply here verbatim; the question is what replaces it:

- **License spectrum across the roster:** Unlicense (MBE) → MIT (TiCon) → **LGPL-3.0 ×5** (ModularUI, GroovyScript, GTCE, AE2 rv6, UniversalTweaks) → **GPL-3.0** (Fugue). Only two of eight candidates are permissive.
- The vestigial corpus shipped only Create snippets (Create is MIT) — there is **no precedent either way** for copyleft material in the DB.
- LGPL/GPL obligations attach to conveyed excerpts; realistic mitigations (short excerpts, prominent per-example source+license notice, `file_url` links to upstream, a `license` column on `mods`, or excluding copyleft repos from snippet storage and storing metadata-only references) are a design decision with real tradeoffs (Open Questions 14–15). Fugue's GPL-3.0 is categorically stricter than the LGPL-3.0 majority and warrants an explicit include/exclude call.
- **LLM-processing angle (flagged, not resolved):** the pipeline sends upstream code to a third-party LLM endpoint for analysis. For permissive repos this is unproblematic; for copyleft repos it is an additional etiquette/terms consideration to record in the per-repo review.
- Whatever is decided, the DB and the pipeline config should **record the per-repo license at ingest time** (the `mods` row and/or DB metadata) so the shipped artifact is self-describing.

### 3.3 Ingestion logistics

- **Acquisition path:** the trees-API pattern in `cleanroom-wiki.ts` hard-fails on `tree.truncated` (:103-105) and per-file raw fetches are sequential and unauthenticated — fine for ~34 wiki pages, unworkable for GTCE-class trees (~160 MB git size). No tarball/codeload/`git clone` path exists in the repo; the closest precedent is the `AdmZip` entry walk in `index-java-api.ts:237-245`. A `codeload.github.com/<owner>/<repo>/zip/<ref>` zipball per pinned ref is the shape that fits existing machinery. GitHub API rate limits: ~60 req/hr unauthenticated, ~5,000/hr with `GITHUB_TOKEN` (which the codebase already honors, [cleanroom-wiki.ts:31-41](../../src/indexer/cleanroom-wiki.ts:31)).
- **Pinning:** most roster repos have no usable release tags for 1.12.2; branches are the unit (`1-12-2-final`, `1.12`, `rv6-1.12`, `master`, `main`). Two branches are effectively frozen (TiCon `1.12` last commit 2021-01-27; MBE `1-12-2-final` repo push 2021-04-16); four are active (Fugue, UniversalTweaks, GTCE, AE2-repo). Pin commit SHAs at ingest and record them in DB metadata — the same drift problem Phase 4 found for the template (Phase 4 R2), and the natural change-detection key for CI (Open Question 18).
- **Default-branch traps:** TiCon defaults to `1.20.1`, AE2 to modern `main` — naive "default branch" ingestion would silently ingest modern code for the two biggest-name mods. Ref selection must be explicit per repo.
- **Subset selection:** GTCE alone is flagship-scale; ingesting whole repos vs curated package subsets (and per-file size caps) is a cost/quality guardrail the design must set (Open Question 21).

## 5. Constraints and risks (consolidated)

**Hard technical constraints:**

- **C1 — Schema reconstruction is by observation.** No fixture DDL exists; `examples_fts`'s column list and all indexes are unrecoverable (§2.2). A.6 already directs the remedy: freeze the schema in a committed migration at rebuild time. The two git-history artifacts (manifest + manifest generator) corroborate but do not complete the picture.
- **C2 — The distribution machinery imposes schema requirements the legacy DB never met.** A rebuild must ship a `metadata` table with `schema_version` matching [dbs.ts:71](../../src/dbs.ts:71) (or bump it), or the auto-update forcing function and any future schema gate cannot work (§2.3). Legacy `0.1.1`/`0.2.0` manifests force a version-continuity decision.
- **C3 — Search is FTS5-prefix only, ranked by curation, not relevance.** No embeddings, no bm25; `quality_score DESC, is_featured DESC` is the entire ranking story (§2.2). Adding semantic search to examples would be new machinery, not reuse (docs embeddings live in a different DB with a different schema).
- **C4 — SRG cross-linking couples two optional DBs with no precedent and no batch API.** `resolveSymbol` is single-shot; helpers are private; handlers open/close per call (§2.6). Index-time resolution needs a held connection and either looping or a new batch method; runtime rendering must define behavior when `mappings.db` is absent.
- **C5 — The LLM pipeline starts from zero and must be reproducible-by-construction.** No LLM code, deps, or endpoint config exist anywhere (§2.5); endpoint configuration must follow the `process.env.X || default` + CLI-flag conventions (`GITHUB_REPO_URL` precedent); golden tests must run offline (canned responses) and follow the licensing-conscious synthetic-fixture style ([mcp-ingest.test.ts:9-21](../../src/mappings/mcp-ingest.test.ts:9)). This is the exact failure that killed the first pipeline.
- **C6 — GitHub ingestion at roster scale needs a new acquisition path.** Trees API truncates (hard error), raw fetches are sequential/unauthenticated, no zipball/clone path exists (§3.3). GTCE (~160 MB git size) defines the scale case.
- **C7 — npm tarball blind spot (inherited from Phase 4 C2).** Only `dist/` + `scripts/postinstall.js` ship ([package.json:38-41](../../package.json)). DB content is unaffected, but any *on-device examples build* option (mappings local-build analog) would require shipping indexer code plus user-facing LLM-endpoint configuration — a strong argument for the maintainer-run model already penciled into [release.yml:185](../../.github/workflows/release.yml:185) (Open Question 19).

**Operational risks:**

- **R1 — Roster licensing.** GPL-3.0 (Fugue) and LGPL-3.0 ×5 vs the DB's verbatim-snippet purpose (§3.2). Per-repo review is an explicit §5.6 gate; snippet policy, attribution mechanics, and the Fugue include/exclude call must be decided before ingestion, not after.
- **R2 — Non-reproducible analysis.** If prompts, model, temperature, and expected outputs are not committed and version-pinned, the pipeline becomes unrecoverable again — the design doc's own named cross-cutting risk ([PROJECT_DESIGN.md:317](../PROJECT_DESIGN.md)). Model drift over time also means re-runs produce different analyses; goldens pin the *pipeline's* behavior, not the provider's.
- **R3 — CI cost/time.** LLM analysis of hundreds–thousands of files must fit a weekly-job budget and a token budget; the `CLEANROOM_API_CHANGED`-style change gate (§2.4) is what makes re-runs cheap — but examples need a different change key (roster SHAs/content hashes recorded in DB metadata).
- **R4 — Roster drift.** Four of eight repos are active; branches are mutable; there are no tags to pin. SHA-pinning + recorded pins are the mitigation (§3.3). Conversely, MBE/TiCon are frozen since 2021 — stable, but their idiom is stock-Forge-era (FG2 toolchain), which the corpus must not mislabel as Cleanroom-era.
- **R5 — Manifest continuity hazard.** Identical to Phase 4 R1: every manifest step downloads the previous manifest with `|| true`; a failed fetch restarts versioning at `0.1.0` and higher-versioned clients skip all future updates. Applies to `examples-manifest.json` from its first publication.
- **R6 — `quality_score` semantics are undefined for the new corpus.** The old conventions are recoverable (avg 0.9, "featured" = ≥0.7 per dead code and the deleted manifest generator), but the rubric that produced them died with the pipeline. Without a committed rubric, the field — and `min_quality`/`featured_only` filters and the stats table — is meaningless decoration.
- **R7 — Known service weaknesses grow with the corpus.** N+1 enrichment (3 queries/example, §2.2), missing loader/version filters (A.1), and the `id || 0` dispatch footgun ([index.ts:292](../../src/index.ts:292)) are tolerable at 3 examples and painful at 300. Fixing them is presumably in scope for "rebuild" but should be stated.
